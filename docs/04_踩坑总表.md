# 一、交付与版本（缓存 / 文案清理）

## A. 交付 / 缓存类（最隐蔽）

### A1. 公式明明改对了，看到的还是旧的 ★★★

- **现象**：COM 读出来对，打开文件看到的还是旧列表
- **根因**：`run_in_wps.py` 的 `Wps` 用 `with` 时 `__exit__` 是 `close(False)`，**不保存**。
  文件里躺的还是旧 XML 缓存；WPS 打开时不一定重算 `FILTER` / `ANCHORARRAY`
- **解法**：`s.close(True)` 真保存一次；用 `chk_cache.py` 离线拆 zip 核对
- **判据**：**COM 读出来对 ≠ 文件里对**

### A2. 文件被外部另存过，改造时用了作基底

- **现象**：改完注入，目标文件没变化 / 改动互相覆盖
- **根因**：文件大小一直漂，改造时用了几小时前的备份
- **解法**：**动手前用 `dump_raw.py` 重抽当前磁盘文件**；判据是源码 / 公式内容，不是文件大小

### A3. 动态数组 COM 写退化成 1 项

- **现象**：计算器 4 格只剩 1 条
- **解法**：离线改 `sheet1.xml`，**保留 `cm="1"` + `t="array" ref="..."`**

### A4. 参考表插行后尾部词条消失

- **根因**：缺 `cm="1"` → 旧式 CSE 数组 → 溢出 ref 冻结
- **解法**：每段 ref 末尾 +N 并补 `cm="1"`

### A5. 溢出区外残留旧值

- **解法**：`clean_spill2.py` 清掉 ref 之外的 `<v>`
- ⚠️ 检查脚本的正则要区分自闭 `<c .../>` 和成对 `<c>...</c>`，
  否则会跨读邻格的值，报假阳性

### A6. 公式括号不配平 → WPS 静默丢弃整条公式，只留缓存值 ★★★

- **现象**：离线改 `sheet1.xml` 注入长 `LET` 公式，单元格**不重算**，还是旧值；
  COM 读 `Range.Formula` 拿到的不是公式而是 `=205.03125`（一个字面量）
- **根因**：生成的公式**少 2 个右括号**。WPS 打不开这条公式时**不报错、不标红**，
  直接把它降级成缓存值；XML 本身 well-formed，`validate_package` 也查不出来
- **解法**：生成公式的脚本里加**括号配平断言**（`count('(') == count(')')`），
  不平直接报错退出，别只验 XML well-formed
- **判据**：**`Range.Formula` 读出来是 `=<数字>` 而不是公式 → 公式被丢了**

## Q. 删除网页内联注释

### Q1. ★★ 单文件 HTML 的 JS 注释会进交付件，删文案必须连注释一起清

- **现象**：要求「网页内联注释的文本都删除」。只删了 `src/template.html` ④ 口径卡里那条可见的
  「已核对：…与参照对象…」后，交付件 HTML 里**还有**参照字样。
- **根因**：`build.py` 把 `src/app.js` **整段内联**进单文件 HTML（占位符 `__JS__` 原样替换），
  app.js 里的注释自然一起进交付件。只动模板那一行，JS 注释里的 `版式参考 <名称>`、
  `已和 <名称> 交叉验证`、`与 <名称> 的核对结论…21240 个数…` 全留着。
- **解法**：删文案时**全局搜**名称及其全部变体（含域名片段、全称、缩写），
  把 `template.html`（可见 + 对应的样式类）、`style.css`、`app.js`（注释 + 自检常量名）、
  `verify.py`（断言改名）、`design.md`（内部文档）全部清一遍，复扫 0 命中后再 `build.py` 重建。
- **判据**：验收不能只看模板，必须**对重建后的 HTML 再 grep 一次**（注释只在 HTML 里，不在 src 里）。
- **★ 注意误报**：base64 载荷与压缩数据里会出现站名的随机子串，
  这类**不是文案**，不要跟着删 —— 判据是「它出现在注释或可见文本里」，
  而不是「字符串出现过」。

### Q2. 删文案后内容变短，会触发 mobile_check 探针的「标题被标签条压住」假红

- **现象**：删掉一条 `.fact` 文案后页面内容变短，`mobile_check.py` 在 390 / 768 误报「版块标题被 sticky 标签条压住」。
- **根因**：探针用写死的 `-58` 偏移去量滚动后的标题位置，内容高度一变，固定滚动量落点就偏，把标题量到标签条底下。
  页面跳转靠 CSS `scroll-margin-top:calc(var(--navH)+8px)`（`style.css:254`），标题已清在标签条下方，无真 bug。
- **解法**：`mobile_check.py` 新增 `secMargin(t)` helper，读**真实的** `scroll-margin-top`（calc 已解析成 px）当偏移，
  既贴合真实点击跳转，又仍能在 scroll-margin-top 真缺失/不足时变红。

## D. 验收脚本类（全是假失败）

### D1. 抽样 N 次结果全一样 ★★★

- **根因**：宏有守卫，前置条件没满足就 `MsgBox + Exit Sub`，**卡片根本没重滚**

- **根因**：融合**只认卡面上已有的词条**，直接写 `I26/I27` 不行

### D3. 融合测试后续全报「每张紫卡最多只能带一个融合词条」

- **根因**：**产物会自动锁定**，洗卡时保留，下一轮就被拒

### D4. pywin32 模块找不到

- **现象**：`ModuleNotFoundError: No module named 'pythoncom'`
- **解法**：换一个装了 `pywin32` 的解释器（当前默认的那个 venv 里没装）

### D5. 输出文件被锁

- **现象**：`PermissionError: [Errno 13] ... R5V.xlsm`
- **根因**：上一个 WPS 进程没退干净
- **解法**：换个输出文件名

# 三、xlsm 与 VBA

## B. VBA 编码 / 注入类

### B1. 注入后工作簿里「所有」宏都报「发生意外」 ★★★

- **根因**：源码文件编码错。`inject.py` 按 **cp936** 写回，
  给它 UTF-8 字节 → VBA 按 GBK 读成乱码 → **整模块编译失败**
  → WPS 对该簿所有宏一律抛 `0x800A03EC`（连没改动的宏、连 `Worksheet_Change` 都挂）
- **判据**：`dump_vba.py` 解出来看到 `鍚嶆牸` 这类乱码
- **解法**：源码文件存 **UTF-8**，但内容要能被 cp936 无损表示
- **别去逐行找语法错误，先查编码**
- 另外 `⇒`(U+21D2) / `−`(U+2212) **不在 GBK 里**，写进源码 `encode('cp936')` 会直接抛错。
  注释里改用 `→`（b'\xa1\xfa'）和 `-`；`×` / `·` / `–` 是可以正常用的

### B2. 分不清是 XML 坏了还是 VBA 坏了

- **Open 阶段就报** → XML / 包结构问题（跑 `validate_package.py`）
- **Open 正常、只有宏报** → VBA 编码 / 编译问题

### B3. `app.Run` 静默吞错

- **现象**：外层看起来正常返回，宏里 `On Error GoTo EH` 弹了框
- **解法**：走 `s.click('CommandButtonN')` 按钮路径；`s.dialogs()` 看弹窗正文

### B4. 按钮名 vs 单元格地址

- `Wps.click()` 要传 **OLEObject 名**（`CommandButton5`），
  **不是**单元格（`M28`）。传错只返回 `'no such button: M28'`，**不抛异常**
- **解法**：先 `print(s.buttons())` 列一遍

### B5. 注入后所有宏报「编译错误: 缺少: 语句结束」 ★★★

- **现象**：2026-09-26 改两条口径时，44 项验收全挂，弹框正文是 `编译错误:\n\n缺少: 语句结束`
- **根因**：新加的**多行注释**，其中一条续行**漏了前导 `'`** → VBA 把注释的第二行当成语句
- **判据**：同 B1（整模块编译失败），但这次编码是对的 → 走 `s.dialogs()` 看弹框正文
- **解法**：续行一律补 `'`；建议改完先 `inject` 再点一次按钮，看有没有弹框
- **教训**：**VBA 的多行注释没有语法结构**，每一行都是独立的 `'` 开头，漏一个就整模块死

### B6. `Me.Range("X")` 读错了工作表（静默失败，最阴） ★★★

- **现象**：新加的 `Public Sub 同步语言参数()` 里读 `Me.Range("H1")` 拿「用语切换」，
  `app.Run` 返回 **OK**、无弹窗，但 `参数!B28/B29` 一个都不动
- **根因**：**模块是 Sheet7（洗卡模拟器）**，`Me` 指向 Sheet7 → 读到的是**洗卡模拟器的 H1（空值）**，
  `Select Case` 永远走 `Case Else`。而「用语切换」格在**计算器**表上
- **判据**：置脏值 → 调函数 → 值没变，说明函数跑到了 `Case Else`（不是没跑）
- **解法**：**跨表取格一律显式指名工作表**：`Worksheets("计算器").Range("H1")`。
  Sheet7 里凡是 `Me.` 的格都要先确认它在不在 Sheet7 上
- **★ 同族坑**：搜索格是 **`洗卡模拟器!I4`**、候选序号格 `I5`（**不是**计算器 B4！），
  取错表会得到"写进去没反应"的假象，白调半天

### B7. `Private Sub` 被 `app.Run` 静默吞掉

- **现象**：`s.app.Run('Sheet7.同步语言参数')` 返回 OK，但什么都没发生
- **根因**：过程写成了 **`Private Sub`**。同模块内调用不受影响，但**外部 Run 找不到**
  （返回成功、不抛异常 —— 与 B3 同源的静默吞错）
- **判据**：换个已知可用的 Public 过程（如 `刷新候选`）对比 Run 结果；或直接看源码的可见性
- **解法**：需要外部 Run 的过程一律 **Public**。本工程里 `刷新候选` 是 `Sub`（默认 Public）所以一直能调

## K. 变体过滤与命名 —— VBA 侧四个坑

### K1. **本体行也要剥形态后缀**
`本体名()` 一上来 `If Not 是变体有本体(...) Then Exit Function` —— 本体直接原样返回，

### K2. **`Replace` 必须显式带 `vbTextCompare`**（最隐蔽的一个）
```vba
If InStr(1, s, f, vbTextCompare) > 0 Then
    t = Replace(s, f, "")          ' ← 错：Replace 默认按**二进制**比对
```
`InStr` 用文本比较时把全角「（」和半角「(」当成同一个字符，于是

`制胜者(主手)`、`制胜者(近战)` 这两把中招。
⇒ 三处 `Replace` 全 `Replace(s, f, "", 1, -1, vbTextCompare)`（保留大小写不敏感）。

## E. 数据 / 表结构类

### E1. 倾向表 J 列猜类别猜错

- J 是 C/D/E 的**扁平展开**（`J2=C2, J3=D2, J4=E2, J5=C3…`），

### E2. 锁定失效

- **根因**：倾向表武器名带**尾随 NBSP（ChrW(160)）**，`Trim$` 去不掉

- **解法**：① 清数据（sharedStrings + 各 sheet `<v>` 首尾不可见空白）
  ② `净名()` + `StrComp(压空格(a), 压空格(b))` **两边同口径**

### E3. 搜索词命中不了

实测**可用**：愤怒(近战) / 赤毒努寇微波枪(手枪) / 惩戒者(曲翼) / 赤毒布拉玛(步枪) / 塞多(霰弹)

> ⇒ 教训：**搜索命不中时先查语言位**（`参数!B29`），别急着怀疑数据。

### E4. ③ 区读到的是旧值

- **根因**：③ 区池按 **I8** 构建；I8 空 → `vcol=0` → 整段静默跳过
- **解法**：验证前先让搜索命中并点一次按钮

### E5. ★★ 融合产物数值漏乘组合系数

- **现象**：网页版写着「融合产物不乘组合系数」—— 实为**沿用了 xlsm 的缺陷**，不是设计意图。
  `融合()` 里写的是 `v = base * disp * vol`，而 `补充词条()`（普通重滚）是 `v = base * coef * disp * vol`。
  结果融合产物数值整体偏小（少乘 0.99 ~ 1.2375 那一档）
- **口径**：融合只替换**词条**，数值会重新生成 → 融合走**同一套公式**：
  `基准 × 组合系数 × 倾向 × 浮动`
- **修法**（`融合()` 第 11 步）：
  ```vb
  comboRow = 组合行(nPos, nNeg)
  coef = CDbl(pWs.Cells(comboRow, 2).Value)   ' 产物固定进正面槽 -> 取增益系数列(B列)
  v = base * coef * disp * vol
  ```
- **规则（通用）**：**沿用 xlsm 行为前，先确认「这是设计还是漏了」**。
  两条路径做同一件事却写法不同，短的那一多半是漏了
- **验证脚本**：`融合数值验证.py <xlsm> [样本数]`，走**按钮路径**点融合，算
  `比值 = 产物值 / (基准 × 倾向)`。旧公式比值落在 `[0.9, 1.1]`，
  新公式落在 `[coef*0.9, coef*1.1]`。取 **2正1负(1.2375)** 或 **3正0负(0.75)**
  时两个区间**不重叠**，一条样本就能判定

## P. 数据表分档格被文本「X1.45」→ Excel 侧池子过滤被毁（网页 + xlsm）

### P1. ★★★ 把数值格填成文本「X1.45」会静默删掉派系词条

- **现象**：需要在格子里也显出「倍率」符号，把 16~18 / 42~44 行（6 条派系伤害）的 G:K 共 30 个分档格
  从数值 `1.45` 了文本 `X1.45`。
- **根因（Excel 侧真 bug）**：洗卡池 `If IsNumeric(dWs.Cells(k, vcol).Value)`、计算器
  `ISNUMBER(INDEX(数据!$G$2:$K$52, MATCH(…), col))` **都是按「格子里是不是数字」来判该词条在当前类别下有没有基准值**。
  文本 `X1.45` 对 `IsNumeric / ISNUMBER` 一律 = false → 这 6 条派系词条会从**洗卡池和计算器下拉里消失**（≠ 数值 0，是直接不在池子里）。
- **网页侧（用 `num()` 兜住，显示正确但和 Excel 当前版不一致）**：
  `export.py` 原 `float(s)` 遇文本会抛 `ValueError` → 6 条派系基准值变 None（④ 区间表 / ③ 计算器 / 融合全线缺档）。
  新增 `num()`：剥前导 `X/x/×` 再 `float()`，网页版仍认成 `1.45`，**不受影响**。
- **解法**：
  - **根治（Excel）**：把那 30 格改回**数值** `1.45`（派系倍率是数值口径）。改回后 Excel 池子恢复，两边一致。
  - **网页**：`num()` 已兜底，无需再动；等 Excel 那 30 格改回数值，两侧行为自然对齐。
- **判据**：**`IsNumeric/ISNUMBER` 判的是「是不是数字」，不是「值是不是 0」**。想给数字加符号，
  用 `NumberFormat`（显示层），**别动存储层**。这条和 Ⅰ 节「派系 1.45 是倍率」同源——数值就是数值。

### P2. 改数据不用动源码，但要先 diff 再重跑

- `export.py` 直接拆 xlsm 的 sheet3（数据表 行 2-52 / 列 G-K）→ `data.json` → `build.py`。
  改数据（如回填融合词缀 r48~52 的 E/F 列）**只改 xlsm，源码一行不动**。
- **重跑前先 `diff` 新旧 `data.json`**，确认只动了该动的几处（比逐行翻表快，还能抓到误改）。回填后
  比对 = **仅 r48~52 的 pre/suf 共 10 处变**，其余 41 条 + 30 个分档格全不动 → 一次过。
- **`build.py` 默认名不带日期**：无参 `build.py` 生成的是 `紫卡模拟器网页版.html`（无日期），
  不是正式交付名 `20260929紫卡模拟器网页版.html`。要覆盖交付件必须显式传位置参数：
  `build.py 20260929紫卡模拟器网页版.html`；`--plain` 默认输出 `紫卡模拟器网页版_无对比.html`。
- **判据最快是逐字节比**：同一份源码 + 同一份 `data.json` 重跑的产物相同，只差 `exportedAt` 时间戳

## H. 业务规则类（改反过）

| 规则 | 结论 |
|---|---|
| 融合时锁定的材料槽 | **自动解锁 + 无条件重滚**，不加"锁定就不重滚"的守卫 |

## Ⅰ. 数值口径类

| 词条 | 口径 | 坑 |
|---|---|---|
| **派系伤害**（行 16/17/18/42/43/44） | 数据表里的 **1.45 是倍率**（＝伤害变 1.45 倍＝+45%）。参与公式的必须是那个 **+45**，不能拿 1.45 直接乘组合系数 | 拿 1.45 去乘 → 倾向 0.5 时算出 1.45×0.5 = 0.72 倍（反倒减伤），明显不对；洗卡区显示成「+1.22%」，就是那条老疑问「派系怎么才 +1.x%」的根因 |
| **后坐力**（行 25） | 全表唯一**方向相反**的一条：正面＝**后坐力降低**（游戏显示 −90%），负面＝**后坐力增加**（游戏显示 +44%） | 正面槽也显示 +90%，玩家照着抄到游戏里就反了 |

**通用教训**：数据表里一个数「看起来像百分数」不代表它就是百分数。
新增/改动词条前先问一句：**这个数在游戏里是怎么显示的？** 派系是倍率、后坐力是反号，
两条都是靠实际卡面数据才发现的，光看数字看不出来。

**实现做法（网页版）**：内部一律存「增减的百分数」（正面槽为正、负面槽为负），
只在显示层做换算 —— `rollBase()`（派系倍率→百分数）、`toGame()` / `fromGame()`（内部↔游戏，含后坐力翻符号）。
③ 区间表只在**正面表**翻符号（负面表本来存的就是幅度，再翻就成负的了）。
派系输入框要给 **4 位小数**：倍率 2 位小数＝百分数只到 0.5，一来一回会把数值磨掉一截（容差 0.011 直接挂）。

**实现做法（xlsm 6.0）**（xlsm 侧同步修改，已改完部署）：
三处必须**一起改** —— 只改 Sheet7 会毁掉「洗卡 → 复制到计算器」链路（两边口径不一致 → 评级算废）。
生成脚本 `源码快照/patch_s7.py`（VBA）+ `源码快照/patch_xml.py`（公式/样式），
验收 `源码快照/verify_xlsm.py`（真机按钮路径，4 组 21 项断言）。

1. **Sheet7 VBA**：新增 `Const 后坐力行 As Long = 25` 与 4 个换算函数 ——
   `是否派系行(k)`（16/17/18/42/43/44）、`基准内部(k, dWs, vcol)`（派系先 `(b-1)*100` 还原成百分数）、
   `游戏值(k, v)`（内部→游戏：派系 `1+v/100`、后坐力 `-v`）、`内部值(k, g)`（它的逆）。
   4 个生成点（融合 / 补充词条 / 生成词条正面 / 负面）取基准一律走 `基准内部()`；
   `写词条(..., Optional ByVal k As Long = 0)` 在**写入时**才换算 —— 数值格存的是
   「游戏里看到的那个数」（派系存倍率、后坐力存负值），
   `更新命名()` 算占比前用 `内部值()` 还原。派系存 **4 位小数** +
   `NumberFormat = """×""0.00;""×""0.00;""×""0.00"`（就是网页版那个 4 位小数的坑）。
   融合产物格同理（走 `是否派系行(prRow)` 分支）；`清融合区` 要把 `NumberFormat` 重置回去。
2. **计算器 sheet1（12 格 D17:F20）**：整条 LET 重写，多算 `fq`（是否派系行）和
   `g4/g5/g6`（三个浮动档各自的结果）：派系 `1+(base-1)*coef*k`、后坐力 `-base*coef*k`、
   其余 `base*coef*k`；`D=MIN(g4,g6)`、`E=g5`、`F=MAX(g4,g6)`。
   ★ **负面槽 / 后坐力是负数，MIN/MAX 会自动挑到对的那一档**，
   正好复刻了「D20 取 1.1、F20 取 0.9」的行为，不用再手写方向。
   系数列：正面槽 17~19 取 `参数!$B$10:$B$13`，负面槽 20 取 `参数!$C$10:$C$13`。
3. **参考·理论区间 sheet2（4 段 × 10 列 = 40 格溢出公式）**：同样是「派系 `1+(rng-1)*…`、
   后坐力 `-rng*…`」两条分支。★ **后坐力的「最小」取浮动 1.1、「最大」取 0.9**（值越负越小），
   和其余词条相反；派系不用反。
4. **显示**：`styles.xml` 加 `numFmt 178` = `"×"0.00`（`dxf` 索引 26），靠**条件格式**只套在派系行上 ——
   计算器 `C17:F20` 判 `MATCH($J17, 数据!$A$16:$A$18 / $A$42:$A$44)`；
   参考表 4 段各判 `ROW()-off = 16/17/18/42/43/44`（off = 2 / 55 / 108 / 161）。

**xlsm 侧新踩的坑**：

| 现象 | 根因 | 解法 |

### Ⅰ-2. 两套倾向口径：读数上限跟着倾向走，历史倾向值另存快照

**两套口径并存**：`web/` = 倾向变动前（`VALUE_MAX=523` / `DISP_MAX=1.55`）；
`倾向改动之后/` = 全库倾向统一 1.2（`VALUE_MAX=404` / `DISP_MAX=1.2`）。

| 项 | 口径 |
|---|---|
| `VALUE_MAX` 推导 | 「基准 × 组合系数 × **最高倾向** × 浮动」：倾向 1.55 → 247.5 × 1.2375 × 1.55 × 1.1 = 523.4，取 **523**；倾向 1.2 → 247.5 × 1.2375 × 1.2 × 1.1 = 404.3，取 **404** |
| 兜底常量 | 必须与 `VALUE_MAX` 同源；`VMAX \|\| 523` 这类硬编码 fallback 会让上限悄悄停在旧值，超界读数被当成真值收下 |
| ⑤区历史倾向值 | `weapons[].disp` 只有一处存放；历史值另存 `dispSnapshot`（按下标一一对应），渲染优先读快照、缺失才回退 `w.disp`；快照真值取自 `web/数据/data.json`（倾向变动前口径），不从改动后的副本取 |
| 数据载体 | `build.py` **不注入 `data.json`**，ZKDATA 硬编码在 `src/template.html`；`data.json` 是 `export.py` 的产物、重跑会被覆盖。快照改动两处都写：`template.html` 的 ZKDATA + `data.json`（供下次 `export.py` 后回填） |
| 主题色 | 样式一律走语义变量（`var(--text)` / `var(--border)` / `var(--brand-text)`）；切主题后截图目视（CDP 切 `data-theme=light\|dark`） |

**★ 校验快照对齐的正确姿势（别只比对数量）**：
快照条数对、名字对，**都不等于下标对**。真正的判据是**渲染后的业务规律**：
各星级列的倾向区间应单调递增（1星 0.50~0.80 → 5星 1.31~1.55）。
这层规律能成立就说明快照与武器一一对齐；只要错位一格，规律立刻崩。

**★ 通用教训**：一个全局量（这里是倾向）改动时，要顺着它把**所有派生的上限、阈值、
反推链**一起重算 —— 派生量是最容易漏的，因为它们看起来是"独立的常量"。

### Ⅰ-3. 生效值与历史值分层（③ 区两个倾向框的语义）

**场景**：倾向统一成 1.2 之后，③区保留「手填倾向」与「对比变体倾向」两个框，
供人把 ⑤区博物馆里的历史倾向值抄进来做对比算。

**分层原则**：「生效值」与「历史值 / 查询能力」是两层：
前者随游戏口径统一为 1.2；后者供人查考历史资料，不随生效值一起回收。

| 控件 | 当前语义 |
|---|---|
| 手填倾向 | 留空 = 跟**统一常量 1.2** 走；填了就是用这个值算 |
| 对比变体倾向 | 自动填**这把武器自己**的**历史值**（博物馆快照） |

## N. 融合产物的浮动**继承两个材料里较高的那个**（网页 + Excel）

### N1. 规则与落点

产物浮动 = **`vol = max(材料A的浮动, 材料B的浮动)`**
（网页 `P.lo + Math.random()` 与 Excel `lo + Rnd()*(hi-lo)` 两处同口径）。公式其余部分不变。

| | 位置 |
|---|---|
| 网页 | `web/源码/框架/app.js` → `doFusion()` 里那行 `var b = rollBase(...)` 之后；新增 `volOf(card, i)` |
| Excel | `Sheet7_当前源码_UTF8.vba` → `融合()` 第 11 步；新增 `Private Function 材料浮动()` |

### N2. ★★ 材料的浮动是**反解**的，不是另存一份隐藏缓存

```
浮动 = 值 / (基准 × 组合系数 × 倾向)
```
网页 `volOf()` / Excel `材料浮动()` 同一个口径；算不出来退中位浮动，结果夹回 `[lo, hi]`。

**为什么别「生成时把 vol 存进隐藏列 / 存进 slot 对象」：**
1. 玩家手填数值还原真紫卡时，根本没有「当初摇出来的浮动」—— 反解出来的才是他想继承的那个数。
2. 缓存会和格子里的数脱节（手改值 → 缓存不更新），界面看着对、结果差一截，极难查。
3. 少一处要同步维护的隐藏区域（清卡 / 换武器 / `镜像下区` 都不用管）。

### N3. 反解时「系数」怎么取

- 第 4 槽（负面槽）用**减益系数**（`参数!C10:C13`，本身是负的：`0 / -0.495 / 0 / -0.75`）；
  其余槽用**增益系数**（`参数!B10:B13` = `0.99 / 1.2375 / 0.75 / 0.9375`）。
- 组合行号由 `组合行(nPos, nNeg)` 决定：`nPos>=3` → 12/13，否则 10/11。
  ★ 判组合要按「**点按钮前卡面上真正写着的东西**」，别按「以为写进去的东西」。
- 派系 / 后坐力先过 `内部值()` 还原成内部口径再除（两边都有这个函数，别绕过）。

### N4. 断言要写**排他性**，光写「落在 0.9~1.1 区间」等于没写

随机值也在那个区间里。真正的判据是：
> 产物值 == `max` 假设，**且**（两个假设差得开时）**!= `min` 假设**。

`verify_fusevol.py` 的 ② 段：手填 4 组 + 自然洗卡 27 组，**102/102**，
每组都同时断言这两条；`domtest.js` 的 `[5b]` 同样三组（A高 / B高 / 两边超界）。

### N5. 新踩的四个坑

1. **`Range(...).MergeArea.ClearContents` 漏括号 = 静默失败**（早就在表里写过，又踩一次）。
   COM 里那只是取方法引用：不报错、什么都不清。症状：以为清掉了 3/4 号槽，实际还在
   → 组合类型判错 → 期望值整段偏（差 48%）。写 COM 一律 `ClearContents()`。
2. **测试脚本自己的变量串台**：① 段用 `ra/rb` 存配方行号，② 段又拿 `ra/rb` 当两个材料的比值
   → 读的是上一批残留的行号，12/12 全判成同一边，类似「功能只走一个分支」。
   **新用例先 grep 变量名。**
3. **注释里别原样写**：断言「第 11 步里没有 `vol = lo + Rnd() * (hi - lo)`」
   被说明的注释触发假红。锚定**代码行**用 `^\s*vol\s*=\s*lo\s*\+\s*Rnd`。

## O. 算法改了、**提示文案没跟着改**（网页）

### O1. 病根：同一个行为有**两个入口**，只改了其中一个

融合产物的浮动「继承两个材料里较高的那个」时，只动了真正算数的 `doFusion()`，
**漏了 `fusePreview()`** —— 融合下拉框旁边那句**实时提示**。于是页面继续显示：

> ~~融合只替换词条，数值会重新随机，按「基准 × 组合系数 × 倾向 × 浮动」落在 X ~ Y 之间~~

新规则下这句话**每一个部分都是错的**：不需要重算随机、不是区间、而是一个定值。
截图直接暴露了这一点（「网页版还是不对」）。

**教训（和「命名有 3 个入口」同宗）**：数据/规则一变，
**先全局搜这个规则的「表述」出现在哪几处**（算法、提示、口径说明、词汇表、导出文本…），
再决定改哪几处。只搜函数名是不够的 —— `fusePreview` 里根本没有「随机」这个词，
它写的是**自然语言文案**，grep 函数名永远找不到。

### O2. 提示里的数**必须复用同一个函数**，别另算一份

新提示里的「固定值」直接调 `volOf()`（＝ `doFusion()` 用的同一个函数）取
`Math.max(volOf(card, m1), volOf(card, m2))`，再套 `b * coef * w.disp * vol`。
★ **不要在 `fusePreview()` 里另写一份公式** —— 两份一定走散，而「走散」正是 O1 的成因。
`verify.py [12]` 现在专门断言函数体里有这句 `Math.max(volOf(card, m1), volOf(card, m2))`。

### O3. 预览也要**守卫**，不能拿中位浮动硬算

改过词条之后，当初选的材料可能已经不在卡面上了（按行号找不到 `m1/m2`）。
此时 `fusePreview` 返回 `bad:true` +「所选词条已经不在当前卡面上了，请重新在下拉里选」，
**不要**退到中位浮动算得出来（`doFusion()` 也会拒）。预览说的话必须和真按下去的结果一致。

### O4. 无头 Chrome 截图的三个坑

1. **`--screenshot` 拍的是视口原点，`window.scrollTo` 的位移拍不进去**。
   想拍页面中段（比如融合提示条），用**负 body 边距**把目标顶上去：
   `document.body.style.marginTop = -(el.getBoundingClientRect().top + window.scrollY - 20) + 'px'`。
2. **手机截图（定宽 iframe）要 `--virtual-time-budget=60000`**。30 s 不够：iframe 里还要再解析
   一遍 344 KB 单文件 HTML，虚拟时间在**加载阶段**就烧掉大半 → 拍到的是「没跑驱动的初始页面」，
   看起来像脚本写错了（易误判）。桌面直载 30 s 够用，手机翻倍。
3. `--screenshot=<相对路径>` 在 Windows 会**拒绝访问**（rc=2），一律给绝对路径。

## Y. `file://` 双击也走本地 ONNX（不被强制 Tesseract）

### 背景
三个问题：① 战争之剑的「范围」读不出来；② 猎鹰轮识别成狼牙；③ 武器识别失败时至少给 2 条词条的置信结果。
逐条定位后结论：**① 和 ② 的根因是识别引擎质量，③ 本就是既有行为**。

### Y1. ★★★ `file://` 被硬编码成 tesseract 是质量事故的根因
`recognize()` 原逻辑：
```js
var engine = opts.engine || (location.protocol === 'file:' ? 'tesseract' : 'auto');
```
即**双击打开 HTML（`file://`）时强制走 Tesseract**，而 Tesseract 是通用 OCR，对紫卡这种固定版式的图远不如本地 ONNX 准。
而识别评估是用 **headless Chrome 以 `file://` 加载本页、强制 `engine:'onnx'`** 跑通的（卡A 正确认出 猎鹰轮），
证明 **ONNX 在 `file://` 下可用**。所以：
```js
var engine = opts.engine || 'auto';   // auto = onnx→paddle→tesseract 兜底链
```
`file://` 现在也优先 ONNX，ONNX 失败自动退回 paddle / tesseract，不丢任何安全性。
改完用同一套评估（去掉强制的 `engine:'onnx'`，走默认 `auto`）重跑 8 张真卡，**结果与强制 onnx 逐张一致，无**。

### Y2. 战争之剑的「范围」(drow=34, NON_PCT 绝对值) 后处理本就正确
单测验证（`buildFromRaw`→`finalize`，干净输入）：
- `战争之剑 / 18 / +92.7% 暴击几率 / +115.9% 近战伤害 / +1.7 攻击范围` → 武器=战争之剑、词条含 `范围[drow=34]`，dropped=0。
- `范围` 在 `NON_PCT_ROWS` 里，`lockIconMisread()` 对它返回 false（不会被当锁图标误读拦下）；
  `攻击范围` 经 `AFFIX_ALIAS` 别名到 `范围`，`rankAffix` 命中 drow=34。
- 各种 OCR 噪声（`攻击范国`/`攻击范围(重击)`/`+1.7 范围`）都能命中 drow=34。
⇒ **读不出来的不是后处理，而是 ONNX/Tesseract 没把那一行检测到**；Y1 的引擎升级（双击也走 ONNX）直接改善检测质量。
  （残留风险：极个别卡「范围」在最底部且 ONNX 也没检测到的极端情况——`scanAllRows` 会兜住一切被检测到的行，但检测不到的行无能为力。）

### Y3. 「猎鹰轮识别成狼牙」本质是 tesseract 把名字读错
ONNX 下：名字读成 `借鹰轮`（借 vs 猎）仍归 **猎鹰轮=92**，狼牙连前 5 都进不了；只有读成 `狼牙轮`(狼牙=95) 才会误归狼牙。
即：只要走 ONNX，`猎鹰轮` 不会变成 `狼牙`。这条事故同样由 Y1 的引擎升级消除。
（数值侧也验证了：猎鹰轮/狼牙 同为近战、disp 1.3 vs 1.36，差距 4.6% 落在浮动窗口内，谁都不会因数值被另一把挤掉。）

### Y4. 「武器没认出也至少给 2 条词条」本就是 finalize 的既有行为
`finalize()` 里词条是由 `sanitizeFinalAffixes(p.affixes)` 生成的，**与武器认没认出来无关**；
武器为 null 时只用 `未识别武器` 占位，词条照出。单测确认：
- 名字=`乱码XXQ` + 3 词条 → 武器被推断填充（或 null），**3 条词条全出**。
- 名字=``（空）+ 2 词条（多重射击 + 范围）→ 武器=null，**2 条词条全出**。
⇒ 这条不用改，已补断言锁住。

### Y5. 结果
- 改动：仅 `ocr.js` `recognize()` 一行引擎路由 + 注释；CRLF 不变（bareLF=0）。

## S. 预处理只挂在 ONNX 上 —— Tesseract 那条路一点都吃不到

要求：预处理必须作用于图片本身，与识别引擎无关 —— 无论什么引擎进来都要先走预处理。

### S1. ★★★ 病根：预处理写在「引擎文件」里，不是写在「图片层」里
- **现象**：紫色边框定位 / 旋正 / 贴模板 / 掩膜 / 去碎块 / 多尺度，这一整套**全定义在 `ocr_onnx.js`**。
  而 `ocr.js` 的 `loadImage()`（**所有引擎的唯一入口**）只走老的 `detectCardBox + alignToTemplate`。
  ⇒ http 打开（ONNX）吃满全套；**`file://` 双击打开（Tesseract，最常用的方式）只吃到老的定位**。
- **机制**：预处理按「先给 ONNX 做定位」的思路写，函数随之放进了 `ocr_onnx.js`，
  ONNX 那一路跑通了就没人回头看 Tesseract 那条路缺什么。
- **解法**：抽 `src/preprocess.js`（**顶层全局、不包 IIFE、不碰任何引擎 API**）。
  `build.py` 注入顺序 `模型常量 → preprocess.js → ocr_onnx.js → ocr.js`（**顺序不能调**，
  公共层必须先于两条识别路径定义）；`ocrtest.js` 里也要先 `eval(preprocess.js)` 再 `eval(ocr.js)`。
- **教训**：**判断一段代码该放哪，看它的输入是什么。** 输入是「图片」→ 公共层；
  输入是「某个引擎的输出/会话」→ 才归引擎。把「图片层」的东西塞进引擎文件，
  等于默认了「只有一个引擎」，而本项目**恰恰有两个引擎**（`file://` 与 http 走的还不一样）。

### S2. ★★ `lumaMask()` 是**返回新画布**，不是就地改 —— 拿「前后像素差」当判据会得到 0
- **现象**：新写的真截图探针报 `maskChangedPx: 0`，类似「增强没干活」。
- **根因**：`lumaMask(cv, thresh)` 内部 `createImageData` + 新建 canvas，**返回 `mc`**，
  传入的 `cv` 一个像素都没动。探针读的是 `cv` 调用前后的差 —— 当然是 0。
- **解法**：**调用方必须用返回值**（`ocr_onnx.js` 两处都是 `const mk = lumaMask(...)` / `lumaMask(...).toDataURL()`，本来就是对的）。
- **同族函数的方向不统一，用先看清**：`dropSmallBlobsCanvas()` = **就地改**；
  `lumaMask()` / `scaleCanvas()` = **返回新的**。
- **教训**：**「工具函数没生效」和「调用方用错了它的契约」是两回事。** 先读它的返回语句再下结论。

### S3. ★★ 「再调一次去碎块抹掉多少像素」不能当判据 —— 幂等必然是 0
- **现象**：探针里 `lumaMask()` 之后再调 `dropSmallBlobsCanvas(mc, 255)`，抹掉 **0 px**。
- **根因**：`lumaMask` 内部第 235 行**已经去过一次碎块**了，第二次是幂等的。
- **正解**：「抹 0」是**对的**（说明不会重复腐蚀笔画），要当成**幂等性断言**；
  但要证明「去碎块真的干活」，得用**合成图白盒用例**：画 1px 噪点 / 4px 噪点（该抹）
  + 3×3 块 / 20×20 块（该留），两个方向（白字黑底 `fg=255` / 黑字白底 `fg=0`）各测一遍。
- **教训**：**一个操作已经跑过一遍的地方，再量它的「增量」永远是 0。**
  要验证「某个步骤有贡献」，必须在**它没跑过**的输入上量。

### S4. ★ 探针 `--dump-dom` 的正则只认 `{` → 数组输出全丢
- **现象**：探针明明跑成功了（DOM 里能看到 `<pre>PROBE[{...}]</pre>`），脚本却报「没拿到探针输出」。
- **根因**：多条结果用**数组**输出，正则写成 `PROBE(\{.*?\})` 认不了开头的 `[`。
- **解法**：`PROBE(\[.*?\]|\{.*?\})`，两种都认。
- **教训**：探针的取值正则要和它自己的输出格式同步改 —— 否则**跑通了也报红**，白慌一场。





## T. 文字探针：加一次「只看哪里有字」的检测喂给定位

要求：在预处理阶段加一次只看有无文字、不看内容的识别，交给后面的定位。

### T1. ★★★ 文字探针直接把 `Image` 传进 `inkBlocks`/`lumaMask` ⇒ `img.getContext is not a function`
- **现象**：`loadImage` 里跑文字探针，双击 HTML（`file://`）打开一识别就整页脚本崩。
- **根因**：`probeText(img)` 直接 `inkBlocks(img)`，`inkBlocks` 内部 `lumaMask(cv)` 调 `cv.getContext(...)`，
  而 `img` 是 `Image` 对象（只有 `naturalWidth/naturalHeight`，**没有 `getContext`**）。
  ONNX 那条路（`onnxDetOnly` → `detPrep`）用 `drawImage` 能接受 Image 所以不炸，**只有 `inkBlocks` 兜底那条炸**。
  ⇒ http 打开且联网时走 ONNX 看不出问题，**一断网 / 双击离线就炸**——典型的「看起来对了没生效」。
- **解法**：`probeText` 里先 `probeCanvas(img)` 把 `Image` 画到一张自然尺寸画布上，再传给 `onnxDetOnly`/`inkBlocks`。
  判据 `img.getContext !== HTMLCanvasElement.prototype.getContext`（Image 上没有这个方法）决定是否转换。
- **教训**：**「能接受 Image 的函数」和「只接受画布的函数」不是一回事。** `drawImage` 两者都吃，
  但 `getContext` 只有画布有。凡是预处理函数，调用前先确认它的输入到底是画布还是图。

### T2. 文字框比碎裂紫色边框更稳 —— 给它「校验 + 兜底」的双重任务
- **动机**：紫色边框是碎裂的，噪声会给零点几度的假倾角；而一行字的走向是连续的。
- **做法**：`probeText` 优先 `onnxDetOnly`（只跑 det，压得住插画噪声），`file://`/离线退回同步 `inkBlocks`；
  两者产出同一种结构 `[{x0,y0,x1,y1,...}]`（原图坐标系）。`textCoverage(quad, boxes)` 算文字中心落在紫框内的比例：
  - 紫框没扫到（`fitToTemplate` 走 `full`）/ `loadImage` 抛错（按原图）/ 覆盖率 < 0.5 ⇒ `fitByText()` 用文字框重定位兜底；
  - 否则保留紫色结果，把字块 + 覆盖率挂 `out.__text` 透出 `text` 给预览画框。




## U. 处理过头：过于模糊反而造成识别阻碍

要求：预处理不能过度处理 —— 图像过于模糊反而造成识别阻碍。需要重新设计前处理 / 后处理思路，
特别是在预处理阶段加一次只看有无文字、不看内容的识别，交给后面的定位。

### U1. ★★★ `detBoxes` 的 `rowH` 引用了未定义的 `yb` —— 整条 ONNX 识别路径静默失败
- **现象**：无头 Chrome 里强制 `engine:'onnx'` 跑真截图，全部报 `ERR yb is not defined`。
- **根因**：`src/ocr_onnx.js` 的 `detBoxes()` 里，`const rowH = (yb - ya) * sy;` 与 `maxGap` 被写在了
  `for (const [ya, yb] of rows)` **循环外面**（加「RivenLens gap ≤ 3×行高」时把逐行变量写到了外面），
  `ya/yb` 只在循环里才有 ⇒ 每次调 `detBoxes` 必抛引用错误。
- **后果**：ONNX 路径整条挂掉 → `onnxPath().catch(...)` 静默回退到 Paddle / Tesseract，
  **看到的是备用引擎的结果，容易误判为在用本地 ONNX**；`window.__stepImages` 也因此设不上。
- **解法**：把 `rowH`/`maxGap` 挪进 `for` 循环体内（逐行算）。
- **教训**：**「静默回退」会把一个必崩的错误藏成「效果一般」。** 有回退链的路径，要单独在**指定引擎**下验证，
  否则永远测的是备用通道。（这次就是靠强制 `engine:'onnx'` 才逮到。）

### U2. ★★ `sanitizeFinalAffixes` 的 `byRow` 算了却没用 ⇒ 重复词条
- **现象**：卡1 出现两条「对克隆尼伤害」（一条带 ×、一条不带）、卡C「暴击伤害」×2、卡D「多重射击」×2。
- **根因**：函数里先用 `byRow`（按对照表行去重）算了一遍，**但 `poss` / `negAll` 直接从 `withM` 过滤，
  `byRow` 从头到尾没被用**（死代码）。多跑投票产生的近重复行（同词条、符号/写法略有差异）于是漏到了最终结果。
- **解法**：`const dedup = [...byRow.values()]`，`poss` / `negAll` 从 `dedup` 过滤。
- **教训**：**算出来没用的中间量 = bug 现场。** 改一处逻辑时先看它上下的变量到底有没有被消费。

### U3. ★★ 预处理「过头」：给 det+rec 喂**硬二值化掩膜**反而更难认
- **现象**（截图）：右栏「掩膜+分界线」是一大坨黑白斑块，浅紫底 + 插画全糊成黑，类似把图处理烂了。
- **根因两处**：
  1. **ONNX 管线**：`onnxFullRows` 跑 5 遍（原图 + 三档硬掩膜 70/90/110 + 整图），
     其中 3 遍喂的是 `lumaMask`（全局对比拉伸 + 一刀切 0/255）——笔画被削、插画糊成黑斑，
     这些**脏识别结果还会参与投票**，把干净原图认对的挤掉。
  2. **界面预览**：右栏自己又做了一次「灰度 >100 一刀切」的糊图（和识别管线无关，纯观感）。
- **正解（对齐业界通行做法）**：强 det+rec **不需要也不该**喂硬二值化掩膜。
   `enhanceForOCR()`：**保灰阶**的柔和增强（2%/98% 分位作黑白点、增益封顶 ≤3×、**不切二值**），
  拿它替掉那三档硬掩膜；预览也改画这张柔和增强图。
- **教训**：**「二值化」是 Tesseract 时代的拐杖，不是普适真理。** 喂给现代 det+rec 的图，
  目标是「对比度够、灰阶完整」，不是「非黑即白」。

### U4. ★ 文字探针驱动分区：name 区用文字框**要加校验**
- 实现「预处理阶段先 det 一次、只看哪里有字」（`detRowsOn`）→ 用它反推 level / name / affix 分区（`zonesFromText`）。
- **level / affix** 用文字框收紧是净收益；**name** 区用文字框能救回一些卡（卡A 由「0 条词条」变 3 条 + 认出 猎鹰轮/Falcor），
  但也可能把武器名整行切没（卡B 从「冰凇/Verglas」变读不出）。
  ⇒ 加一道「像不像一条武器名」校验（够高 ≥5%H 且够宽 ≥30%W 才采信，否则退回固定百分比）。
- **教训**：**探针给的是「哪里有字」，不等于「这段字是什么」。** 拿位置信息去收紧分区前，先加一个形状校验兜底。

### U5. 真·识别 A/B 评估（关键工具）
- 无头 Chrome 里跑**真实 ONNX 管线**（`recognize({engine:'onnx'})`）对 `testimg/` 8 张真截图出结果，
  一次性拿到 level / 武器 / 词条（含 dropped、原始行）。改动前后各跑一遍即可 diff。
- **★ 本机无头 Chrome 可直连网络**，**不需要 `--proxy-server`**。

## V. 分区实测重标定 + 后处理 4 处缺陷

**起因**：预处理过度处理导致图像过于模糊，反而造成识别阻碍。需研究**分界线怎么画、区域怎么分、怎么通过对比度灰度二值判断分界线**。
研究方式限定为自行编写分析脚本、自行观察几张卡的共性与区别。

### V0. 研究方法（工具留在 `web/` 下，随时可复跑）
| 脚本 | 作用 |
|---|---|
| `web/分析_分界线.py` | PIL+numpy 复刻定位→632×800，逐行 mean/median/dark%，并试 6 种分界线判据（`divider` 模式看离散度） |
| `web/分析_版面.py` | 把卡画成 63×76 的 ASCII 灰度图 + 逐行剖面（**模型读不了图时靠它「看」版面**） |
| `web/标定_区域.py` | ★ 最有价值：无头 Chrome 跑真 ONNX det+rec，把**每一行的 y/x 比例 + 识别内容**全打出来 = 区域标定地面真值 |
| `web/eval_ocr.py --dir <目录>` | 真识别 A/B（支持 `--dir`，可用任意目录的图） |

### V1. ★★★ 分界线**扫亮度扫不出来**
9 张真卡实测 6 种亮度判据（灰度最大落差 / 二值暗带 / 二值白占比落差 /  prevBright>80→<55 / median<95 连续 12 行）：
- 候选值散布 **0.24 ~ 0.84**，std 0.107~0.21，极差最大 0.55 —— **插画区自己就有大片暗部、页脚亮度又会回升，没有稳定的明暗台阶**。
- 真正稳定的是**文字几何**：词条行距恒 ≈**0.05H**、末条词条锚在 ≈**0.775H**、页脚锚在 ≈**0.84H**、容量/等级锚在 ≈**0.10H**；
  名字块（=分界线）随词条条数在 **0.44~0.67** 之间浮动。
⇒ **分界线 = 最下面那段连续文字块的上边界**，由文字探针算（公共层 `preprocess.js` 新增 `textBlockTop(rows, H)`，
  从最后一行往上走、遇断档 >1.6×行距就停）。识别管线和界面预览现在共用这一个算法。

### V2. ★★★ 旧 `findDivider` 返回的是**错的值**，却被拿去当尺子
实测返回 0.45 / 0.618 / 0.748 / 0.805 / 0.813 / 0.815 / 0.818 / 0.835（**落在页脚回升段**），

## X. 组合死规矩 + 全局扫描 + 预处理/后处理必须是全局的

三条硬约束：
① **词条组合只有四种：2+0 / 3+0 / 2+1 / 3+1。两条必定都是增益，四条必定最后一条是减益；识别到三条时需按数值判断是 2+1 还是 3+0**；
② **预处理与后处理必须作用在全局，不能只对某一个引擎生效**；
③ **对不上的图也要做全局扫描看有没有匹配的，不能因为紫卡模板没对上就不识别**。

### X1. ★★★ 组合只能由一个函数定，不能让各行的符号各自为政
旧逻辑是「取 3 条正面 + 补 1 条负面」，各行的符号各管各的 ⇒ 能输出 `1+1` / `2+2` / `4+0` 这些游戏里不存在的组合。
⇒ 新增 `decideCombo(list, rank)`：**先按认出的条数定组合**，再往里填。
| 认出条数 | 组合 | 依据 |
|---|---|---|
| 1 | 1+0（兜底） | — |
| 2 | **2+0** | 硬约束：两条必定都是增益 |
| 3 | 2+1 或 3+0 | 见 X2 |
| ≥4 | **3+1** | 硬约束；减益永远在卡面最后一行 |
符号与规矩矛盾时**按规矩纠正**（`affixAsPos` / `affixAsNeg`）：负号 ↔ 正号只改符号、数值取绝对值；
派系倍率 ×0.51 ↔ ×1.49 关于 ×1 对称，翻转是 ×(2−倍率)（×0.51 = −49%，对称增益就是 +49%）。

### X2. ★★★ 3 条时「仔细看」靠的是**数值**，不是符号
2+1 的增益系数 **1.2375** / 减益 **0.495**，3+0 的增益系数 **0.75** —— **差 1.65 倍**。
⇒ 拿候选武器的**倾向**反解浮动（`值 = 基准 × 组合系数 × 倾向 × 浮动 × (等级+1)/9`，浮动只在 `[0.9,1.1]`），
看哪种组合能解释这几个数。**负号读丢（误判 3+0）与负号误读（误判 2+1）都靠它翻盘**。
打分：`(解释不了 ? 100 : fit) + 符号不一致 ? 2 : 0` ⇒ 符号明确时以符号为准，只有符号那一档根本解释不了才翻盘。
（`comboFitBest` 遍历该类武器取最小 fit；`rank` 必须先算好再调 `sanitizeFinalAffixes`，否则反解不出来。）

### X3. ★★★ 两版定位取并集时，**顺序必须以整图版为准**
文字兜底裁切后，`裁切版的行 + 整图版独有的行` 拼起来的顺序**不是卡面顺序** ⇒
死规矩「减益永远在最后一行」会挑错行（实测那张横条卡：并集后把「−144% 暴击几率」排到了中间，
结果把「火焰伤害」判成减益）。⇒ `mergeClassified(整图版, 裁切版)`，整图版的行就是真实卡面顺序。

### X4. ★★★ `inkBlocks` 写死前景色 ⇒ 白底黑字的图一个字块都找不到
`lumaMask` 后按 `d[p*4] === 255` 找连通域，等于假设「白字黑底」。
但**别的图**常常相反 —— 实测 623×182 那张横条卡 **90% 的像素亮度 > 224**（白底黑字），
连通域只找到整片背景，`w > maxW` 被过滤 ⇒ **文字探针返回 0 个框**（`文字框=0`），定位与覆盖率全废。
⇒ 新增 `inkPolarity()`：亮的占多数就是背景，前景取暗色；并**按正确方向再抹一次碎块**
（`lumaMask` 内部那次是按 fg=255 做的，对这一路等于往前景里加噪点）。
同一类坑：**`onnxDetOnly` 一个框都没给出时也不能就这么算了** —— 要退回 `inkBlocks` 再扫一遍（只有抛错才回退）。

### X5. ★★ 文字兜底裁切会裁掉画面 ⇒ 整图版本必须留着一起扫
`fitByText` 只保留有字的那块。裁对了更好，**裁错了反而比整图认到的还少**
（实测那张横条卡：整图 4 条、裁完只剩 2 条）。
⇒ `alt.__fullCanvas = out`，识别时**两版都扫一遍取并集**（即「全局扫描」这一要求）。
`globalOnly()`（`fit.mode` 为 `full`/`raw`）时则按内容认：新增 `scanAllRows()` ——
与位置无关，一行只要能解析出「符号+数值」且名字对得上词条表（≥62）就是词条，不管它在图哪个角落；
另外按内容认武器名（≥70）与容量消耗（6~18 的两位数）。
备用引擎那条路同样：模板没对上时改认**整张图**（`ocrRegion('affix', …, { top: 0, bottom: 1 })`）。

### X6. 改 `return` 的位置会把调试块落到 return 之后
把 `return finalize(...)` 换成 `finish()` 时，紧跟其后的 `window.__dbgRows` 调试块变成了
**永远执行不到**（`eval_ocr.py` 里 rows 全变 0，会误以为「一行都没认出来」）。
⇒ 移动 return 时先看清它后面还挂着什么。**有回退链的路径要靠指定引擎的 A/B 才验得到**。

### X7. 预处理 / 后处理「是不是全局的」—— 现在有断言盯着了
| 环节 | 结论 | 断言 |
|---|---|---|
| 定位 / 旋正 / 贴模板 | **全局**：`loadImage` 里 `fitToTemplate()`，与引擎无关 | `fitToTemplate(img)` 存在 |
| 掩膜 / 去碎块 / 文字探针 | **全局**：都在 `src/preprocess.js`（公共层） | **公共层代码里不得出现任何引擎名**（剥注释后查） |
| 后处理（符号还原 / 派系 / 去重 / 组合判定 / 反推武器） | **全局**：都在 `finalize()` 里，三条识别路径都调 | `finalize(` 调用 ≥4 次 |
| 各引擎自己的东西 | 只在引擎内：`onnxFullRows` 的多跑投票、`buildConsensus` 的多阈值投票 | — |
⚠ 剩下的一处不一致（如实记账）：Tesseract 那条路的二值化走的是自己的 `binarizeAuto`（就地改、阈值 70/100/130 三档投票），
没复用公共层的 `lumaMask` + `dropSmallBlobsCanvas`。功能等价，但**不是同一份代码** —— 此处未改动，
因为 `file://` 双击那条路没法在本机真机验证。要统一的话必须先在能联网的机器上跑一次 Tesseract A/B。

### X8. 结果
10 张真卡（engine=onnx）**逐条与基线一致**，唯一变化是 `bf7bd829` 那张横条卡
`fit` 由 `full`（没定位到）变成 **`text-axis`**（文字框 31，真的定位到了），词条仍是 4 条且顺序不变。


## R+. 四种词条组合实测，修掉 4 类识别错误

### R6. ★★★ 卡面名字行右半那条拉丁串是**紫卡自己的名字**，不是武器名 —— 拿它认武器就会认错
- **现象**（截图）：「**冰凇变成锤子了**」—— 识别结果给了**弧电振子锤**（Arca Titron，近战），
  于是「多重射击」被判成「这把武器没这条属性」丢掉，3 条词条只剩 2 条。
- **根因**：`rankWeapon` 会把卡面读到的拉丁串拿去和武器的 **en 列**比。而卡面上那串
  （`Cari-satricron` / `Laci-croniata`…）是**紫卡 mod 自己的名字**，跟武器毫无关系 ——
  它撞上「Arca Titron」拿到 `simScore 67 − 5 = 62` 分，正好够 `finalize` 里
  「≥62 就退回最佳候选」的兜底线，于是顶替了真正该匹配的中文名。
- **解法**：en 列**只有 ≥80 才采信**（能到 80 的只有真·英文客户端读出的英文武器名）。
  中文没读出来时结果就是 `weapon = null` → 状态行提示「没认出武器名，请手选」——
  **宁可留空手选，也绝不猜一把武器**（猜错的连带损失是词条按错类别被丢）。
- **教训**：**先搞清楚那串字符是什么，再决定能不能拿它当匹配键。** 实现把拉丁串当
  「英文武器名」用了十轮没炸，只是因为它的测试卡中文名都读对了；中文一读错，噪声立刻变主证据。

### R7. ★★★ 锁图标被 OCR 读成一个数字 → 把真正的负面词条**投票投死**（3正1负 → 3正0负）
- **现象**（截图）：「**3+1词条变成3+0词条了**」，而且负面槽的位置冒出个 `+5.00 切割伤害`。
- **根因**：被锁定的词条行首有 🔒，OCR 常把锁读成个位数（同一场景已记录过「+6 重击效率 P」）。
  多阈值 + 子带会把这个误读重复 3~4 遍，`finalizeAffixEntry` 按**裸票数**就把真正的
  「−127.1% 切割伤害」（1 票）压掉了；已有的「% 集群 ×2」只够打平，不够翻盘。
- **解法**：`lockIconMisread(a)` = **个位数 + 没读到 % + 该词条在卡面上必然带 %**
  （`NON_PCT_ROWS = [20,27,28,34,16,17,18,42,43,44]` 之外的 40 多行；穿透/初始连击/连击持续时间/范围
  本来就是绝对值，派系显示 ×1.45，都不算）。命中就：投票时整簇 **×0.5**、最终结果里**直接拦下**
  并计数（`res.dropped` → UI 计入「另有 N 条没认出来，请手动补」）。
- **教训**：**噪声不只会「混进来」，还会「重复进来」把真信号投死。** 加权投票要考虑
  「同一种误读被多个阈值重复观测」这件事，不能只按票数。

### R8. ★★★ 派系词条卡面写**倍率**（`×0.51`），不带负号 —— 旧逻辑当正词条、还把倍率塞进数值框
- **现象**：鳄神卡（3正1负，负面是「对 Grineer 的伤害」）识别后负面槽是空的，
  或者把 `0.51` 当正数值填进去。
- **根因**：`sanitizeFinalAffixes` / `ocrApply` 都只认 `-` 开头的才是负词条；
  而派系词条在卡面上是 `×0.51`（减益）/ `×1.51`（增益）。另外卡面中文名带拉丁派系名
  （「对 Grineer 的伤害」），`parseAffixes` 会把拉丁剔掉只剩「对的伤害」，三个派系名同时打到
  67 分并列 —— 会认错派系。
- **解法**：`factionRowOf()` 按派系关键词（grineer/corpus/infested、克隆尼/科普斯/异变体）
  **直接定位到数据表行**（16/17/18）；`factionSign()` 判 `×<1` 为减益；
  `ocrApply` 按 `(倍率−1)×100` 还原内部口径（×0.51 → −49 落负面槽，输入框显示回 `0.5100`）。
- **教训**：**「负号」不是负面词条的唯一表示法。** 凡是有特殊显示格式的词条（派系倍率、
  后坐力反向），都要单独问一句「它长什么样」，别假设都带负号。

### R9. ★★ OCR 把相邻两行并成一行 → 旧逻辑只取最后一个数值，**前一条词条整条消失**
- **现象**：猎鹰轮卡（3正1负）识别后「+61.9% 攻击速度」不见了，组合变成 3正0负。
- **根因**：`parseAffixes` 一行只取「符号+数值+名称」的**最后一个**匹配（设计意图是防锁图标噪声），
  而词条行间距小，OCR 经常把两行并成一行，于是前一条被静默丢掉。
- **解法**：一行里出现 **≥2 个「带 % 且词条名能对上对照表」**的数值时**全部收下**
  （这种配对本身很强，噪声配不出），y 依次 +2 避免同组互投。
- **顺带修的坑**：`parseAffixes` 取名字用 `re.lastIndex`，而 `while` 循环最后一次 `exec`
  **失败时会把 `lastIndex` 重置成 0** —— 原实现就是这么写的，靠后面清理把数字删掉掩住了，
  只在派系行留下 `x 对 Grineer 的伤害` 这种前缀。用匹配自身的 `index + [0].length`。
- **教训**：**「取最后一个」这种防噪声写法，和「合并行」是互斥的。** 要么两个都处理（区分强弱配对），
  要么明确接受其中一种损失 —— 别默认只有一种会发生。


## AG. 口径显示词订正（只改显示，不动识别逻辑）

### AG1. 口径显示词的规范写法
口径显示词的规范写法（共 7 类）：
- 投射物飞行速度 → 投射物速度
- 收起武器时自动装填 → 收起武器时弹匣每秒自动装填
- 后坐力 → 武器后坐力
- 范围 → 攻击范围
- 震地伤害 → 震地攻击伤害
- 格挡角度 → 招架角度
- 对"派系"伤害 → 对"派系"的伤害（即「对克隆尼伤害」→「对克隆尼的伤害」之类）
澄清：国际服就叫「对Corpus的伤害」、国服就叫「对科普斯的伤害」，不用改识别逻辑或其他的，**只改显示逻辑**。

### AH1. bug①：名称在前 + 跨行 + 字形相近（卡帕压力枪 Sati-decipia）
要求：「收起武器时弹匣每秒自动装填X%」是文字在前、数值在后且带换行，需要特殊处理，并纳入字形相近的判断机制。
ONNX 原始行实测（分界线 y=325）：
```
486: 收起武器时弹便每秒目      ← 名称前半，且「匣」读成「便」
486: 收起武器时弹甲每秒目      ← 同一片段被读两遍，「匣」读成「甲」
525: 动装填+100.4%            ← 名称后半 + 数值（名称在前、数值在后）
```
旧逻辑三个地方同时卡住：
1. `parseAffixes` 的正则只认**数值在前、其后跟名称**（`/([+\-…])?\s*(\d…)\s*(%?)\s*(?=[\u4e00-\u9fffA-Za-z（(])/g`）→ 名称在前的整条**静默消失**；
2. `mergeFragmentLines` 只处理「数值在前」的折行 → 名称被折成两半时拼不回来；
3. `CONFUSE` 里没有 匣↔便/甲、自↔目 → 即便拼回来也对不上表名。

### AH2. 修复三件套（名称在前 + 折行 + 形近字）
- **`mergeFragmentLines` 补折行分支**：当前行「有汉字、无数字」时，向后找**紧邻的、以汉字开头且结尾是数字或 %** 的短行（≤20 字），拼成一行再解析（避免把下一整条词条吃掉）。
- **`parseAffixes` 补「名称在前」规则**（在 `if (!last)` 处）：
  `/^([\u4e00-\u9fffA-Za-z][…]*?)\s*([+\-−–—‐‑﹣×xX✕⨯*±])?\s*(\d{1,3}(?:\.\d{1,3})?)\s*(%?)\s*$/`
  命中且名称部分含汉字就收。
- **CONFUSE 补两组**：`['匣','甲','便']`、`['自','目']`；并新增 `levConf` / `simScoreConf`（把 CONFUSE 视为相同的编辑距离），`rankAffix`  `Math.max(simScore, simScoreConf)` —— ★ 词条名只走**纯编辑距离**时，形近字一律算错字；`simScoreConf` 补上「字形相近的判断机制」这一环。

  变体代价 `SETTLE_W.wVar=1.0`（≈ 1 级；早期取 1.5），但**不能压过 absMean** ——
  ★ 另加两条护栏：容量 `rankCostOf(...)=0`（一眼读准）时 **`pinRank` 钉死等级**、单条数值偏 11% 不推翻；名字分 ≥92 时 **`nameLocked` 锁武器**，不许换同族变体。
  变体卡（卡面只印本体名）是系统性情况，不是偶发错误。
- **输入说明**：识别模块除图片外还接两类文本（`parseLabeled`/`parseShorthand`/`parseFreeText`），
  三类输入最终汇到同一套 `ocrApply`，判定规则一致。
- ★ **自校验两轮**：
  ① 正向 47 项常量 ↔ 源码逐条比对；
  ② **反向扫描「文档里出现但源码里查无此数的量」** —— 该方法曾揪出 4 处写错：
  `0.035`（源码里没有）、重复行判据、CONFUSE 组数、组合系数。
  ★ 反向扫描比正向核对更抓错：正向只验证「写的在不在源码里」，
  反向验证「源码里有的有没有漏写 / 写错」。


## W. 认不出武器名时，用词条反推类别并填该类里最置信的一把

要求：已扫描出词条时，按词条表反推候选武器（如近战武器洗不出「变焦」时），再取该武器类型中置信度最高的一把填入。

### W0. 先搞清「词条表」里那条约束藏在哪
`stats[i].v` 五个槽按 **[步枪, 霰弹, 手枪, 曲翼, 近战]** 排，**`null` = 该类别洗不出这条**。
以「变焦」为例：`[59.99, 41.994, 80.1, 59.99, null]` —— 近战那格是 `null`。
⇒ 认出来的每条词条都给一个「允许的类别集合」，**求交集**就是这张卡可能的武器类别（`catsFromAffixes`）。
（★ 槽位顺序是从 `export.py` 导出的数据里核对过的，不按「步枪/手枪/霰弹…」的字面顺序。）

### W1. ★★★ `WEAPON_TABLE` 漏挂 `disp` ⇒ 整条反推静默失效
`weaponValueFit` 第一句是 `if (!isFinite(w.disp)) return NaN;`（没有倾向就无从反解浮动）。
但 `WEAPON_TABLE` 建表时只拷了 `idx/cn/intl/en/cat`，**没拷 `disp`** ⇒ 每把武器都返回 `NaN`
⇒ 所有候选被淘汰 ⇒ 只剩旧的「名字 ≥62 就填」兜底，**新逻辑一行都没生效，而且不报错**。
⇒ **凡是「构造函数 = 返回 NaN」的判据，先确认喂进去的对象真有这个字段**（这条和 U1 同一个病：
有回退链的路径静默失败）。修：`WEAPON_TABLE` 补 `disp: w.disp`。

### W2. ★★★ 兜底分支没过类别关 ⇒ 「带变焦」的卡被塞一把近战
名字没命中时有个兜底：`top.score >= 62` 就拿来填。这条**没有过类别关**，
于是「带变焦」的卡（词条已经明说不是近战）因为名字分凑够 62 被塞了一把近战（猎鹰轮 score=100）。
⇒ **兜底分支和主分支必须受同一套约束**（类别关 + 倾向吻合），不能因为「是兜底」就松掉。

### W3. ★★★ 名字分没有底线 ⇒ 「水松」被填成「圣装猎豹」
`rankWeapon` 的候选分是降序的，但**低分段全是噪声**：排名 20~40 分那几条常常只共用一个字
（「水松」→「圣装猎豹」score=14）。一路扫到底 ⇒ 填了一把不相关的枪，**比留空还糟**。
⇒ 加 `if (all[i].score < 45) break;` —— 和 `matchAffix` 对词条名用的那条底线同一个道理
（**同一条底线在两处含义一致，改一处要同步想另一处**）。

### W4. ★★ 要求类别唯一才填 ⇒ 永远填不出来
硬约束（可洗性矩阵交集）通常砍不干净：实测卡「水松」砍到 `步枪/霰弹/手枪/曲翼`，
再用「倾向能不能解释这些数值」筛（`catsAlive`）后停在 **`步枪/手枪` 两个**。
原写法 `if (alive.length !== 1) return null;` ⇒ 这张卡永远空着。
⇒  **`if (!alive.length) return null;`**，在**所有**还活着的类别里挑 `weaponValueFit` 最小的那把。
填出来的武器类别仍然落在反推的类别里（别的类别已被硬约束排除），**不会比留空更糟** ——
留空则需在几十把武器里自行查找。

### W5. 顺序：先把词条定下来，再反推武器（不能反）
`finalize` 里必须先 `sanitizeFinalAffixes` → `catsFromAffixes` → 再挑武器。
反过来的话武器已经用「没清洗过的词条」挑完了，类别关就成了摆设。
返回体新增 3 个字段透给界面：`weapon.cat`（短名）、`weapon.inferred`（= 是按词条推断的）、
`weaponCats`（可能的类别，`catsAlive` 更窄所以优先给它的结果）。
★ `inferred` 一定要一路传到界面文案 —— **不能让人以为名字真认出来了**：
「武器名没认出来 —— 按认出来的词条推断这是一把 **步枪**，已先填入 **德拉**…请核对或手选」。

### W6. 容量消耗 → 等级：`DRAIN2RANK` 两份副本必须逐字一致
反推要用等级（`值 = 基准 × 组合系数 × 倾向 × 浮动 × (等级+1)/9`），但卡面右上角读出来的是**容量消耗**
（R2：6⇒rank0、18⇒rank8）。`DRAIN2RANK` 在 **`ocr.js` 与 `app.js` 各有一份**
（识别模块反推武器 / 计算器填等级），改一份忘另一份 = 反推出来的等级和界面显示的等级对不上。
⇒ `verify.py` 已加断言：两份副本做 `findall` 后**逐字比对**，不一致直接红。

### W7. 置信度怎么定（这套判据是核心判据）
1. **硬约束**：某类别洗不出这条属性 ⇒ 直接否（`rowBaseOf` 返回 `NaN`）。
2. **硬指标**：拿候选武器的**倾向 `disp`** 反解浮动 ——
   `值 = 基准 × 组合系数 × 倾向 × 浮动 × (等级+1)/9`，浮动按定义只可能落在 `[0.9, 1.1]`，
   **解释不了的直接淘汰**（比单纯按名字打分硬得多）。
3. **容忍一条失配**：卡面读数是 OCR 出来的，小数点读丢之类会歪掉一条；
   因为一条歪了就否掉整把武器 ⇒ 反推等于失效。所以 `miss > 1` 才否。
4. 打分 = `失配条数×5 + 反解浮动与 1 的平均偏差`，**越小越置信**。

## Z. 卡面头行「武器名 + 紫卡生成名」连读成陌生单词 ⇒ 冰凇认不出

### 背景
英文客户端冰凇紫卡截图报 bug：正确识别出的文字与后面的（紫卡生成名）连在一起，变成陌生单词去匹配中文 —— 实际仍是冰凇。

### Z1. ★★★ 根因：det/rec 把头行两段并进同一框，连读成一串陌生单词，旧整串相似度被 ≥80 门槛挡掉
紫卡卡面头行天生是两段——「武器英文名 + 紫卡生成名」（英文客户端读出来就是 `Verglas Maga-visipha` / `Cari-saticron` / `Laci-croniata`）。而 det/rec 经常把两段并进同一个文字框、连读成一串（实测 rows 里就是一整条 `Verglasblaga-visipha`）。
旧 `rankWeapon` 只做一次整串相似度：走 `simScore` 的「包含」分支拿 `95 - |长度差|` ≈ 78~84 分，正好落在 `se >= 80` 那道门槛之下 ⇒ 武器整把认不出，退回按词条硬猜（实测被猜成「赤毒布拉克」）。

### Z2. ★★★ 修复：rankWeapon 的 en 列改「按词 / 前缀」命中
新增 `latinTokens()` 工具（按非字母数字切开、NFKC 归一化、转小写）。在 `rankWeapon` 的 `if (se >= 80) ...; else` 分支里加：
- 拉丁串切开后**任一段与武器英文名逐字相同**即为头行命中；
- 两段全粘住（没有任何分隔符）时退一步看**前缀**，但要求英文名 **≥6 字母** —— 这样既能认 `Verglasblaga-visipha`，又能避开紫卡生成名的碎片误命中（`Acridra` 会撞上 `Acrid`，但 5 字母够不到 6 的门槛）。
- 给分 `84 + 字母数`（上限 96）：名字越长越可信，Prime 变体自然压过本体。

### Z3. parseName 纯拉丁卡要把其余拉丁行并进来
卡面头行被拆成两行（`Verglas` / `Maga-visipha`）时，`pickNameLine` 只挑一行 —— 纯拉丁卡（中文名没读出来）会把武器名那段整条丢掉。⇒ `parseName` 在 `cn` 为空时把其余纯拉丁行也并进来，一起交给 `rankWeapon` 的「按词/前缀」判据；有中文名时保持原样。

### Z4. 误命中护栏不破
验证脚本确认一批紫卡生成名前缀绝不撞武器真名：`Cari-saticron` / `Laci-croniata` / `Visi-calididex` / `Visican` / `Acri-critatis` / `blaga-visipha` 等都返回 null（不猜武器、不认成锤子）。既有的 R6 护栏（`Cari-saticron` 不认成 Arca Titron）仍然成立。

### Z5. 结果
- 改动：`web/源码/识别/ocr.js` 三处（新增 `latinTokens` + `rankWeapon` en 列按词/前缀分支 + `parseName` 纯拉丁并入）；CRLF 不变（bareLF=0）。`web/ocrtest.js` +8 条（75→83）。
- 关键断言：连读串 `Verglasblaga-visipha` → 冰凇(91)、带空格 `Verglas Maga-visipha` → 冰凇、Prime 头行 `Verglas Prime Maga-visipha` → 圣装冰凇(96)；只有生成名 / 生成名碎片 → null；整卡回放武器=冰凇且 `inferred=false`（不是按词条硬猜），英文词条（Damage / Critical Chance）照样认出。

## AA. 负号丢失 + 冰凇被认成德拉（武器名匹配顺序重构：字形→错别字→拼音→其他）

### 背景
两张截图报 bug：① 负号疑似没识别 / 被当噪声去除，要求「识别的数字前面没有 + 时按负数处理」；② 冰凇被认成德拉，要求「调整识别执行顺序：先看字形 → 看错别字 → 看拼音 → 再看其他匹配规则」。

### AA1. ★★★ 冰凇→德拉根因：中文名两字全错（冰凇→水松）⇒ 旧 rankWeapon 中文列 0 分 ⇒ 落进值拟合兜底乱猜武器
真机（`eval_ocr.py` 跑 `web/testimg/`）确认：`卡2_冰凇`/`卡B_冰凇` OCR 把「冰凇」读成「水松」两字全错，旧 `rankWeapon` 中文列只做一次整串相似度、`水松`↔`冰凇` 交集为 0 → 0 分，武器认不出 → 按词条值硬猜成 德拉 / 艾弗旺-5木星（`inferred=true`）。排除检测/引擎问题（上轮 `_diag2/_diag3` 已验证直接喂正确 name 文本无此 bug）：根因是**武器名匹配口径缺少「近形/谐音」容错**。

### AA2. ★★★ 修复：武器名匹配顺序重构为「字形 → 错别字 → 拼音 → 其他」
新增 `CONFUSE` 可混淆字表（水↔冰、凇↔松、信↔言、凤↔风、刚↔钢、女↔文、魔↔订、猎↔借）+ `commonCharsConf()`；pypinyin 预生成 `PINYIN_MAP`（607 字）+ `pyScoreOf()`。`rankWeapon` 中文列按四级打分取最高：
① **字形**：整串相等 100；包含 `95-|差|`；`simScore`；
② **错别字（主修复）**：两字名同位置可混淆 → 92、单字 → 85、`commonCharsConf≥2` → `min(96, 84+4×共享数)`；
③ **拼音（tier-3 兜底，防碰撞）**：凇/松 都 → `song`；长度不同 ≤70、长度相同 ≤90（避免「水松」误撞 3 字「歌颂/送葬者」）；
④ **其他**：英文列 `nen` 作为最后一级，`se >= 80` 才采信。
⇒ 水松→冰凇 92 分命中；冰松→冰凇；水松+`Cari-satricron`（紫卡生成名）→ 冰凇；言条·枢密→信条枢密。

### AA3. ★★★ 负号丢失根因：decideCombo 把「读到的符号」喂 fit，丢负号 → 2+1 永远拟合不过 3+0
真机复现：丢负号的不是冰凇（3+0 本无负号），而是 **信条枢密 `−31.1% 重击效率` 负号被读丢**，旧 `decideCombo` 把读到的 `+`（丢负号后）喂 `weaponValueFit`，2+1 假设下末行是 `+` → 拟合失败 → 3+0 胜（减益被吞成正面）。按「无 + 即负」字面实现会误伤无符号增益，**不采用**。

### AA4. 修复：2+1 假设强制末行当减益再拟合（与 X2 同思路），fit 不可解重罚 + 未知武器乱加负号护栏
`decideCombo` 对 2+1 假设 `rows` 构建时 `if (o.neg && i===n-1) sign='-'`；pen 逻辑：该有负号却落在非末位 → pen=2；最终行 `sc = (isFinite(fit)?fit:1000) + pen + (o.neg && !isFinite(fit) ? 500 : 0)`。fit 不可解重罚 1000；2+1 不可解再 +500（避免未知武器无负号时乱加负号）；`rank` 必须先算（X2 约束）。

### AA5. 结果
- 改动：`web/源码/识别/ocr.js`（`rankWeapon` 重构 + `decideCombo` 强制末行负 + 新增 CONFUSE/PINYIN 辅助）；CRLF 不变（bareLF=0）。`web/ocrtest.js` 83→89（修正 2 处 stale 断言 + 新增块）。

## AB. 武器名变体 tie-break（卡面只出本体，分数打平优先无变体前缀）

### 背景
依据 `OCR识别错题本_最终版.xlsx`（5 sheet：全部识别错误 422 / 武器识别错误 275 / 词缀识别错误 72 / 常见错误字符统计 57 / 数字识别错误 75）审阅，并实测 275 个武器错例（`_diag_confuse.js`）：**56 个是「正确武器（本体）与变体（圣装/信条…）分数打平 = 96，只输在排序」**—— 变体名字包含本体（如 圣装绝路 含 绝路），两边同加分还是平，CONFUSE 救不了；扩充混淆对还会制造误匹配（武器认对 212→209，净差 −3）。紫卡武器名约束见 AB1。

### AB1. ★★★ 约束：卡面只出本体，变体由数值判断
规则：紫卡卡面只会出现本体和「有变体无本体」的武器；填入计算器的武器名由数值判断是否为变体。OCR 直接输出的结果不可能是「绝路prime」这类带变体前缀的名字，只能是「绝路」，再由数值判断是否为变体。⇒ 工具 OCR 出来的武器名**永远是本体**（或「有变体无本体」武器本身），绝不可能凭空认出带前缀的变体（圣装/信条/赤毒…）；变体由 disposition 数值事后判断再回填计算器。

### AB2. ★★★ 加 CONFUSE 反而变差（关键发现，方向纠正）
扩充 CONFUSE（抢↔枪、品↔晶、钟↔锤、全↔圣、创↔剑、力↔刀/刃、妆↔杖、利↔莉、链↔锤、必↔步、少↔步）后武器认对 212→209（净差 −3）：56 个「错误」实为变体打平歧义（CONFUSE 救不了），新加的对还制造误匹配。⇒ 撤回 CONFUSE 扩充，改走 tie-break。

### AB3. ★★★ 修复：rankWeapon 排序加三级 tie-break
新增 `VARIANT_PREFIXES = ['圣装','信条','赤毒','棱晶','异变','试用型','枢议']` + `hasVar(name)`；`rankWeapon` 末尾排序（在 `b.score - a.score` 之后）加：
① `hasVar(a.row.cn) - hasVar(b.row.cn)` —— 分数打平优先**无变体前缀**者（卡面只出本体，绝不凭空出「X Prime」）；
② `Math.abs(a.row.cn.length - ncn.length) - Math.abs(b.row.cn.length - ncn.length)` —— 名字长度最接近 OCR 串者优先；

## R. 网页版加「截图识别」（复用既有 OCR 逻辑）

### R1. ★★ 换了一张图、图还没读完就点「识别」→ 认的是**上一张**

- **现象**：端到端用 5 张样本图连跑，第 2 张起状态行一直停在「截图已就绪」，计算器始终是空的。
- **根因**：`ocrTake()` 是「FileReader → 解码 → 检测卡片 → 对齐模板」的**异步**链。
  第一张失败后按钮被 `ocrEnableGo(true)` 放开，第二张的读图还没结束按钮就已经可点，
  于是「点识别」认的是上一张（或上一张的空图），随后读图完成又把状态行覆盖成「截图已就绪」——
  看起来就像「点了没反应」。
- **解法**：加 `OCR_LOADING` 标志，`ocrTake()` 一开始就 `ocrEnableGo(false)`，
  读图成功 / 失败 / `clear` 三条路都要复位；`ocrRun()` 里 `OCR_BUSY || OCR_LOADING` 任一为真直接返回。
- **教训**：**任何「耗时的准备步骤 + 一个动作按钮」的组合，都要把按钮在准备期间锁死**，
  只在准备完成后放开。光锁「动作进行中」不够（那是 `OCR_BUSY`），准备阶段也要锁。

### R2. ★★ 卡面右上角的数字是**容量消耗（drain）**，不是等级

- **现象**：样本卡右上角恒为 `18`，而「段位」是另一个数，一度按「等级」理解。
- **根因**：那是 mod 的容量消耗。按官方数据：**rank 0 = 6、rank 8 = 18**，中间档按 +1.5/级 取整。
- **解法**：`DRAIN2RANK = {6:0,7:1,8:1,9:2,10:2,11:3,12:4,13:4,14:5,15:6,16:6,17:7,18:8}`，
  查不到（读空 / 读错）就退回满级 `P.maxRank`。计算器「当前等级」要吃 **rank**，不是 drain。
- **教训**：**看不懂的数字先核对权威来源，不按字面语义直接套用**（跟「属性方向先拆 sheet1.xml 看 Excel 原文」同一条）。

### R3. ★★ 识别出来的数值还原成内部口径，**别走 `fromGame()`**

- **现象**：`fromGame(v,row)` 对派系行做的是 `(v-1)*100` —— 那是按「界面显示倍率 1.45」写的。
- **根因**：**这是本工具自己的显示口径**；游戏里派系紫卡写的也是 `+45%`，
  所以 OCR 读到的 `45` 本来就是内部值，再过 `fromGame()` 会变成 `4400`。
- **解法**：`internal = (sign==='-' ? -1 : 1) * |value| * dirOf(drow)` —— **只过一次 `dirOf()`**。
  后坐力（行 25）方向相反，卡面正面槽写 `−90%`，落进计算器是**正面槽 / 内部 +90**，
  显示层再翻回 `−90.00`，一条链自洽。
- **验证**：`domtest.js` 里专门断言「后坐力 `−90%` → 第 1 槽（正面）、输入框 `-90.00`」。
- **教训**：**同一个数在系统里有几套口径，就要数清楚有几套**；从其它入口取数据时，
  先问「这个数走哪套口径」，别拿一个写好的换算函数就往里套。

### R4. jsdom 跑不了真 OCR（要 canvas + 联网）—— 换成桩，只测「结果 → 计算器」那条线

- **现象**：`domtest.js` 里走真 `RivenOCR.loadImage` 会卡住（jsdom 的 `Image` 不解码 data URL，
  `onload` 永不触发），用例直接挂死。
- **解法**：测试开始前把 `window.RivenOCR` 整个换成桩（`loadImage` / `hasImage` / `recognize` 三个函数），
  然后照真实操作走一遍：**派发一个带 `clipboardData.items` 的 `paste` 事件** → 等按钮解禁 → 点「识别」→
  断言计算器的 `#combo` / `#rank` / 四个 `krow` 下拉 / 四个 `kval` 输入框。
  `#ocrZone` / `#ocrGo` / `#ocrStatus` 都在 `#calc-body` **外面**，`renderCalc()` 重建内层也不会让引用失效。
- **教训**：**测不了的那一层就换桩**，把「本次新写的那段」隔离出来测；不要因为「底层跑不动」就整个放弃验收。
  真识别那一层另有 node 冒烟测试 + 既有实测记录。

### R5. 识别引擎是按需联网的（页面仍是离线单文件）—— 本机无外网只能验到「读图」

- **现象**：无头 Chrome 里跑端到端，5 张图都停在「识别失败：Tesseract.js 脚本加载失败（需联网）」。
- **根因**：PaddleOCR（`@paddleocr/paddleocr-js@0.4.2/+esm`）和 Tesseract.js（`5.1.1`）都从 CDN 按需拉；
  本机验收环境的 Chrome 连不上外网（用一页 `fetch` / `import` 探针确认过）。
  这条报错说明**两段引擎链路都按顺序走通了**，不是页面 bug。
- **解法**：`ocrRun()` 的 `catch` 里把这类报错翻译成人话：「识别引擎要从网上加载，请连上网络后重试」。
  `verify.py` 额外断言**进度文案里不许出现引擎名 / 阈值 / 掩膜**（进度文案不暴露算法细节）。
- **教训**：**「验不到」要如实记账，不能算「验过了」。** 这里验到的是
  「5 张真实样本图 × 读图 + 状态机 + 按钮锁」，**真识别结果没验到**；
  下次在能联网的机器上必须补跑一遍。

### AD3. ★★★ 武器后坐力（drow 25）方向相反 + 按位置定槽位
- `dirOf(25) = -1`：卡面 `+X` 是**减益**、卡面 `-X` 是**增益**（与普通词条反过来）。
- **槽位判定以「真·末条 = y 最大」为准，不是数组末项**：双扫合并（`mergeClassified`/`mergeDual` 整图版在前、裁切版独有行追加）会打乱数组顺序，原 `dedup[n-1]` 不是卡面最末条。按真实 y 坐标（`lastByY = y 最大那条`）判定末条：真·末条若是后坐力 → 占负面槽（卡①）；后坐力在上方 2 条以上（非末条）→ 占正面槽（卡②/卡③）。
- **后坐力输出符号必须由 `recoilOut(a,isNegBox)` 翻成 app.js 方向公式要的值**：`app.js` `ocrApply` 用 `internal = (sign==='-'?-1:1)*|v|*dirOf(25)` 定槽（<0→负面框）。所以正面槽（`isNegBox=false`）输出 `-`（`→ internal=+|v|>0` 落正面框、显示仍由 `dirOf` 翻成「降低」）、负面槽（`isNegBox=true`）输出 `+`（`→ internal=-|v|<0` 落负面框）。**移除 `recoilOut`（原样输出卡面空符号）会让真实链路 `internal<0` 落负面框、把真负面挤成 `neg[1]` 丢掉（惩戒者卡③ 实测），因此必须保留 `recoilOut` 翻号**。`dirOf(25)` 仍由 app.js 管「显示值翻不翻」，但「喂给它的符号」必须由 `recoilOut` 决定，ocr.js 不能留空（否则留空符号经 `(sign==='-'?-1:1)=+1` 再乘 `dirOf(25)=-1` 直接判成负面）。
- **4 词条（3+1）「最后一个是负面」也以真·末条为准**：`recoilNeg` 只在 `recoilIsLast`（后坐力 === lastByY）时成立；否则后坐力当普通词条，真·末条的普通减益（如卡③ 弹药最大值 drow22）占负面槽。写死 `if (n>=4) recoilNeg=true` 会把「非末条的后坐力」也强塞负面槽、挤掉真负面 → 见 AD8。
- **绝不能因后坐力负号提前结束**：所有词条行在武器名行~段位行间都照看，后坐力只是一条普通候选行。

### AD4. 数值/噪声清理

### AD8. 后坐力专属处理 refinement（修 4 词条把真负面挤掉）
- **根因（残留 bug）**：`sanitizeFinalAffixes` 里写死 `if (n >= 4) recoilNeg = true` —— 4 词条时**无条件**把后坐力塞负面槽，不管它到底是不是卡面最末条。双扫合并打乱数组顺序后，真·末条是别的减益（卡③ 惩戒者：真负面是 `drow22 弹药最大值`，后坐力 `drow25` 是增益且不在末条），被强塞负面槽 → 真负面消失、combo 塌成 3+0。
- **修法三处（ocr.js `sanitizeFinalAffixes`）**：
  1. **y 坐标透明透传**：全链路（`classifyRows`→`scanAllRows`→`mergeGlobalScan`/`mergeClassified`/`mergeDual`→`buildFromRaw`→`parseAffixes`）带 `{text, y}`，无真实 y 时退回数组序；`lastByY = y 最大那条` 才可靠。
  2. **`recoilNeg` 仅在 `recoilIsLast`（后坐力 === lastByY）时成立**；否则后坐力当普通词条，真·末条的普通减益（如卡③ drow22）占负面槽。2 词条全正面、3 词条后坐力=末条仍按符号规则（+/−/空白）定槽位与组合。
  3. **去掉 `recoilOut` 翻号（★ 已裁定这是错的）**：AD8 让后坐力原样输出卡面符号（`pushAffix` 直接 `out.push({a:x.a})`），以为「方向交 app.js `dirOf(25)` 处理」。但 app.js 对**空符号**走 `(sign==='-'?-1:1)=+1`，乘 `dirOf(25)=-1` → `internal` 直接判成负面，后坐力被塞进负面框、真负面（弹药最大值）挤成 `neg[1]` 被丢（真实 app 截图复现：惩戒者后坐力进负面、弹约最大值漏掉；巨浪后坐力显示负号）。**AD9 恢复 `recoilOut`**。
- **结果**：ocrtest / domtest（桩 RES 自带 `sign:'-'`）都过，但真实链路 bug 没被任何测试抓到。卡②/卡③ 后坐力期望符号由 `-` 改 `''` 反而把桩测试「恰好正确」掩盖了真实链路错误。
- **结果**：两条验收路都过，**★ 但都是假绿——漏了「ocr.js 真实输出 → app.js 落槽」，见 AD9。**

### AD9. `recoilOut` 必须保留（修真实链路后坐力落错槽）

### AD12. 定价引擎有两份实现（Python + 前端 JS）——必须逐条对拍
- **背景**：定价算法原本只在 `紫卡工具包/tools/riven_price.py`（命令行 / 出单文件页面）。接进模拟器后
  `web/源码/框架/priceref.js` 是它的第二份实现，一份 Python 一份 JS，**同一套口径两处代码**。
- **坑**：两边只要有一处漂移（相似度权重、分层容差、离群倍数、`%g` 式数值格式化），
  页面和命令行就会给出不同的价，而且**没有任何报错**——用户看到的是两个都能跑的工具，数字不一样。
- **纪律**：
  - `priceref.js` 是 `estimate()` 的**逐行翻译**，不许「顺手优化」。常量（`TOL 0.05` / `NEG_BONUS 0.12` /
    `VAL_MIX 0.45` / `WIDE_POW 6` / 离群线 6 倍）两边必须同值。
  - 改任一边后跑 `tools/check_priceref_parity.py --n 400`：随机抽挂单，逐条比
    `p25/p50/p75/n_used/n_same/exact`，**不一致即退出码 1，不许发版**。
  - 新增判断条件（如「词条没填全就不给三档价」）时，Python 命令行与前端必须**同条件**，
    否则会出现「页面不给数、命令行给数」的分裂。
- **词条量纲坑**：WM 上派系词条（`damage_vs_*` / `damage_to_*`）存的是**倍率**（1.06 = ×1.06，0.6 = ×0.6），

  Python 侧 `%g` 直接印数字（命令行有「相似度」列做上下文，不额外加 ×）。
- **数据不手改**：`web/源码/数据/zkpricedb.js` 由 `tools/make_priceref_js.py` 生成，
  头顶写着「自动生成，不要手改」。口径改了必须重跑生成脚本，否则页面用的还是旧库。

### AD15. ★ 负词条只看「有无」+ 译名自建表格 → 两处系统性偏差
- **现象**：负词条折价只看「有没有负」，同把武器上代价悬殊的负词条（如 -变焦 与 -基础伤害）
  等价处理；抓单侧的词条译名自建表格，与游戏内文案对不上。
- **真相 1（严重度）**：estimate() 只判 `hasNeg === 候选有负` 就 +0.12，「-变焦」和「-多重」
  等价。控制变量实测（同武器同 3 正比负）只有 13 组样本，纯数据学不出曲线 →
  走「常识规则 + warframe-items 面板」：0~3 档乘数，候选价按 `price×m_q/m_c` 折算。
  同一条负 = 真同款 +0.12，不同条但都有负只 +0.04。
- **真相 2（译名）**：抓单侧 `grab_riven_attrs.STAT_ZH` 是自建的，「对 Corpus 伤害 /
  状态伤害 / 弹药上限 / 后坐力」与游戏内文案对不上，`make_priceref_js.NAME_PATCH` 还把
  科腐者(Techrot)/炽蛇军(Scaldra)写反。唯一译名源 = `源码/填表/wm-stat-id.txt` 国服名列，
  `tools/stat_names.py` 只做 slug→WM英文名 的机械路由；词库可读时路由缺项直接中止。
- **坑**：
  - warframe-items 字段是驼峰 `criticalChance/procChance/damage`（damage 键小写），
    不是文档里的 `damageTypes`；第一版抓出来全是 0。
  - `attacks[]` 里 `crit_chance` 是**百分数**（29 = 29%），与 `criticalChance`（0~1）不同刻度。
  - 暴击/触发要取**本体与 Incarnon 形态较大值**（托里德 15% vs 29%），变体（Prime/Wraith）
    一起取最强（ignis 家族按 Ignis Wraith 算）——WM 紫卡是家族维度，行情由最强形态决定。

    JS 分位数必须 `Math.floor` 对齐。

    与残留相同的行被静默拒绝 → 场景结果诡异地反向。每个场景先清空 4 槽再填。
